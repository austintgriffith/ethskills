# Skill improvement

Use when asked to improve a skill or when an observed workflow failure warrants a proposed correction. Observing a weakness during another task does not authorize editing or publishing a skill.

1. Capture the triggering request, actual instructions used, available capabilities, observed behavior and desired outcome. Separate a content defect from missing tooling, ambiguous intent or a dependency/version mismatch.
2. Read the relevant skill-authoring guidance available in the host and the affected skill's callers/references. Use `reflect` to derive a lesson from evidence rather than inventing a universal rule from a hypothetical edge case.
3. Make the narrowest authorized change that alters the faulty decision. Keep common constraints in the entrypoint and conditional procedures in linked references. Prefer one canonical source over duplicated discovery, adapter or evidence rules.
4. Validate name/description frontmatter and local links. For behavioral changes, create realistic cases with raw project inputs, allowed side effects and observable acceptance criteria. Exercise positive cases and near misses; do not use wording matches as proof of better agent decisions.
5. Keep generated fixtures/evidence isolated from production source. Report which cases actually ran, their observations and remaining untested combinations. A case description is not a passing evaluation or a support claim.
6. Inspect for accidental blanket autonomy, stack migration, required vendor models, default URLs and unnecessary panels. Preserve permission and read-only boundaries. Publish changes, submit feedback or open a PR only within explicit authorization.
