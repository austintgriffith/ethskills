# Build

Use for scoped implementation or a behavior-preserving refactor inside Pilot's execution loop. Ship supplies dApp coverage, not a competing coordinator.

1. Define observable acceptance behavior and inspect the affected callers, storage/data shape, package boundary and existing tests. For a refactor, name behavior that must stay the same. Avoid speculative compatibility layers and unrelated cleanup.
2. Settle consequential design uncertainty using Design. Use `blast-radius` when changes can reach other packages, ABI consumers, storage, events or indexers. Sequence coupled changes so each unit has a meaningful check.
3. Implement one checkable unit using repository-native patterns and compatible dependency APIs. Preserve compiler settings, remappings, client major versions and wallet architecture. For Solidity, apply security and relevant standards; check decimals, authorization, callbacks and external failure handling. Treat ABI, event and storage changes as consumer-facing decisions.
4. Use `tdd` when a cheap behavioral test sharpens the requirement. Otherwise choose meaningful checks without adding tests that only mirror the implementation. Use testing for fuzz, invariant or fork techniques when the changed behavior warrants them.
5. Run that unit's targeted native checks and inspect results before dependent implementation. Repeat steps 3–5 for the next unit. Broaden checks when dependencies or failures justify them. Route actual contract/app behavior to Verify. A build alone proves neither wallet flow nor live contract behavior. Preserve a working repeatable check for multi-session work; use Trace pickup before stopping.
6. Before finishing a wallet dApp, load [Verify](../../verify/SKILL.md) and execute its [browser/wallet procedure](../../verify/references/browser-wallet.md). Follow the user's saved browser choice and host rules to prepare disposable Chrome/Chromium and the requested real wallet. Configure the actual owned local node, fund the disposable account with test assets, and execute the affected user journeys through app controls and observed wallet prompts. Correlate receipts, independent state and refreshed UI. A simulated provider or CLI roundtrip cannot replace this check. If blocked, report the attempted setup paths and exact missing capability or host restriction, rather than stopping at "the shared preview has no MetaMask". Do not wait for the user to invoke Verify.
7. Inspect the final diff for unrelated changes and temporary instrumentation. Report what changed, why, check results and outstanding verification. A required real wallet assertion that remains blocked prevents an overall verification PASS. Do not commit, open a PR or deploy unless the task authorizes that action.

If work is parallelized, establish exclusive write ownership or isolated worktrees before edits. Review combined changes and their interactions; delegate reports are evidence to assess, not a substitute for integration checks.
